# Spec: Side Glance v0.1.0 stable release

> Filed by: Codex `/root`
> Status: approved for implementation and publication
> Last updated: 2026-08-29

## One-line summary

Promote the current, verified Side Glance beta into the first stable `0.1.0`
release without overstating provider support, then prove that npm, GitHub,
native artifacts, Homebrew guidance, and public documentation all resolve to
the same immutable build.

## Problem

Side Glance has a complete public beta release path, but its normal public
discovery surfaces still disagree. GitHub has only prereleases, so
`/releases/latest` is absent. npm's `latest` dist-tag still points at the old
`0.1.0-beta.1` ownership publication, whose metadata reports the obsolete MIT
license, while the current package and repository are Apache-2.0. Public install
guidance must therefore name `@beta` explicitly.

Publishing a version tag alone would not be sufficient. The package version,
publish channel, lockfile, changelog, CLI recovery commands, website, package
README, structured data, tests, protected source commit, and release artifacts
must all move together or the project would present a superficially stable tag
with beta-era behavior around it.

## Approved outcome

### Stable package and release

- `packages/cli/package.json` and its lockfile entry use `0.1.0`.
- `publishConfig.tag` is deliberately changed from `beta` to `latest`.
- A protected annotated `v0.1.0` tag names the exact verified `main` commit.
- The existing release workflow publishes the assembled npm tarball with OIDC
  provenance and finalizes a non-draft, non-prerelease GitHub release marked
  Latest.
- The release contains the npm tarball, manifest, checksums, generated Homebrew
  formula, and the supported/experimental native archives already defined by
  the release policy.
- Existing beta versions and npm's `beta` dist-tag remain immutable historical
  records; they are not deleted or repointed as part of this release.

### Stable public journey

Homebrew remains the recommended durable installation. npm fallback and `npx`
examples use the stable channel (`side-glance@latest`) wherever an explicit
channel is useful. Current website, CLI, package, machine-readable, and support
copy describe Side Glance v0.1 as stable rather than as an unpublished or
public-beta candidate.

Provider-specific evidence boundaries do not change: Claude Code and Codex
remain the locally contract-audited integrations, while Gemini, OpenCode v1,
and Aider remain experimental. A stable Side Glance package is not a claim that
every provider integration is stable.

### Badge and metadata correction

The Apache-2.0 license remains declared in the repository and package. Once
`0.1.0` owns npm's `latest` dist-tag, npm-backed consumers such as the README's
license badge can resolve the current Apache-2.0 metadata instead of the stale
MIT metadata on beta.1. CDN badge caches may take time to refresh; the registry
metadata is the source of truth.

## Non-goals

- Declaring Side Glance 1.0 or changing runtime behavior.
- Promoting experimental providers or Intel macOS to supported status.
- Replacing the tag-driven, multi-artifact workflow with Changesets solely to
  mirror Ultracite's npm-focused release architecture.
- Deleting historical prereleases, moving protected tags, or rewriting npm
  beta history.
- Redesigning the landing page or changing the lifecycle theme.

## Boundaries

**Always:** write observable stable-contract tests before production changes;
keep package, lockfile, docs, structured data, and CLI guidance synchronized;
run every repository and applicable browser gate; use protected merge commits;
tag only the exact green `main` commit; verify public bytes and metadata after
publication.

**Ask first:** any version other than `0.1.0`; any attempt to change or remove an
existing public release, dist-tag, or protected tag; any scope expansion into
new runtime behavior.

**Never:** publish from the release branch or `staging`; bypass a protected
check; move or reuse `v0.1.0`; attach different bytes to an existing version;
claim experimental integrations are stable; add a long-lived npm token.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Stable tag disagrees with package or source | High | Exact version/tag validator, protected-tag and main-ancestry checks |
| npm publishes but GitHub finalization fails | High | Draft-first GitHub release, byte-comparing retries, immutable fix-forward policy |
| Public copy still installs beta | Medium | Source-level stable-contract tests across CLI, docs, and site |
| Badge continues to show MIT temporarily | Low | Verify npm `latest` license directly; allow for Shields cache refresh |
| Homebrew formula lags the release | Medium | Keep tap credentials separate; open generated-formula PR after assets exist |
| Stable wording overstates provider maturity | High | Preserve explicit provider/platform qualifiers and claim tests |

## Rollback and recovery

Before tagging, repair or revert through a new protected PR. After npm or GitHub
publication, never move the tag or replace bytes. Deprecate a defective npm
version when appropriate and fix forward with `0.1.1`; leave `0.1.0` as the
audit record. A transient workflow retry is permitted only when it reuses the
same tagged workflow and byte-identical bundle. Homebrew is not updated until
the immutable release succeeds, so a tap failure can be repaired independently.
